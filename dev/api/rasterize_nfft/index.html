Rasterization & NFFT

Two ways to make a real-space image from the projected tessels and their intensity weights, without the dense polyft matrix. See Direct imaging methods for examples.

Rasterization

Each pixel receives the exact overlap area of each tessel (Sutherland–Hodgman clipping) times its intensity. No Fourier transform is involved.

rasterize_adjoint!(grad, res_img, proj_west, proj_north, pixel_weight, pixsize; cx, cy)Adjoint (transpose) of the rasterization, for gradients

The image is indexed img[iy, ix]; proj_west = proj_north = 0 falls on pixel (cx, cy).

rasterize_adjoint!

The exact transpose of the rasterization: it gathers pixel values back to the tessels, weighted by the same overlap areas.

grad[p] = pixel_weight[p] * pixsize^2 * sum_{iy,ix} res_img[iy,ix] * Area(tile_p ∩ pixel)

Both are threaded over tessels.

NFFT

The polygon Fourier transform on a regular frequency grid: Gauss–Legendre quadrature points inside each tessel, summed with one adjoint NFFT.

Return value layout

polyft_nfft_forward returns a Complex{T} array of shape (nx÷2+1, nx) in the standard rfft layout:

  • rows: rfftfreq(nx, 1/pixsize), from 0 to the Nyquist frequency 1/(2*pixsize) cycles/mas;
  • columns: fftfreq(nx, 1/pixsize), in FFT order (zero frequency at index 1).

irfft(F, nx) gives the real-space image; fftshift centres it:

img = fftshift(irfft(F, nx))

Sign convention

F[k] = Σ f_j exp(-2πi k·r_j). NFFT.jl's adjoint has the opposite sign, so the sample positions are negated (pos = -r/L, L = nx*pixsize); ifftshift then takes NFFT order (k = -N/2, …, N/2-1) to FFT order, and the first nx÷2+1 rows form the rfft layout.

build_gauss_samples

Maps [-1,1]^2 onto each tessel bilinearly, splits it into nsub × nsub sub-squares, and puts an ngauss × ngauss Gauss–Legendre rule in each. Returns (xs, ys, fs): the positions (mas) of the points and their weights (intensity × Jacobian × Gauss weight).

Total samples: (ngauss * nsub)^2 * Npix.

Sky images for OITOOLS

FITS image cubes from which OITOOLS computes visibilities; see Exporting sky images for OITOOLS.

ROTIR.sky_grid — Function
sky_grid(params, tess, tepochs; data, oversample = 4, fov_factor = 6.0, min_nx = 256, pixsize, nx)
sky_grid(components, tepochs; ...)
    -> (; pixsize, nx, diameter, extent, mb_per_plane, reason)

A pixel size and image size for a sky cube, with the reason for each.

Pixel size (mas): 1/(2ρmax)/oversample, with ρmax the longest baseline in data (cycles per radian). Without data, 1/64 of the largest projected stellar diameter.

Image size: the whole system plus (fov_factor − 1) diameters of the largest star (for one star, fov_factor diameters), at least min_nx, rounded up to an even 2·3·5-smooth size.

On the ζ And coverage, OITOOLS reproduces ROTIR's visibilities to 1.3e-4 with a field of 2 diameters, 3e-5 with 4 (closure phases 0.28° → 0.05° rms) and about 5e-6 with 12; 256 pixels is about 11 diameters there.

A binary's field grows with its separation while the pixel size is set by the baselines; mb_per_plane gives the memory per Float32 plane. pixsize or nx given explicitly are used as is.

ROTIR.render_sky_cube — Function
render_sky_cube(params, xmap, tess; tepochs, wavelengths, pixsize, nx,
                rendering = :bandlimited, intensity_model = :linear,
                normalize = :plane, secondary = nothing, mjd = nothing,
                bandwidths = nothing, T = Float32) -> (cube, meta)
render_sky_cube(components; tepochs, wavelengths, ...) -> (cube, meta)

Render the surface xmap (on tess, with geometry params), or several components, as sky images: an (nx, nx, nλ, nt) array in OITOOLS' layout (see sky_layout), one plane per wavelength and epoch. nx must be even.

Each component is a NamedTuple (; params, x, tess, secondary = false, offsets = nothing); offsets holds one (west, north) displacement in mas per epoch (nothing: at the origin). A binary is two components, the companion offset by its orbit. Mutual occultation is not drawn.

  • tepochs are ROTIR epoch times (the same numbers create_star_multiepochs takes); mjd, when given, is recorded alongside them.
  • wavelengths in metres. With intensity_model = :linear (Rayleigh–Jeans) every channel has the same SHAPE; with :planck the contrast — and a binary's flux ratio — change with λ.
  • rendering: :bandlimited (default) is the exact polygon Fourier transform on the FFT grid, inverse-transformed; OITOOLS reproduces ROTIR's visibilities from it to about 1e-5, and it has small negative pixels near the limb. :area gives each pixel the exact facet overlap times intensity: positive and flux-conserving, for display, with visibilities attenuated by the pixel's sinc (2.7e-3 measured).
  • normalize: :plane, every plane sums to 1 (as OITOOLS imaging expects); or :relative, relative flux across channels and epochs (the λ⁻⁵ or λ⁻⁴ factor of the intensity is restored), scaled so the brightest plane sums to 1.
  • bandwidths (m), optional: recorded as EFF_BAND in the CHANNELS table, like OI_WAVELENGTH. The planes themselves are monochromatic at wavelengths.

meta carries everything write_sky_cube records and check_sky_cube needs: pixel size, wavelengths, epochs, per-plane flux before normalisation, rendering, intensity model, the components and their parameters (meta.params is the first component's).

ROTIR.write_sky_cube — Function
write_sky_cube(path, cube, meta; comment = "") -> String

Write a cube from render_sky_cube as FITS: the (nx, nx, nλ, nt) primary array with a celestial WCS, plus CHANNELS and EPOCHS tables and the model's parameters (PARAMS).

The first axis increases East (CDELT1 > 0) and the reference pixel is nx÷2+1, the layout OITOOLS uses (OITOOLS' own writefits writes CDELT1 < 0 and CRPIX = nx/2). Pixel scales are in degrees with CUNIT set; OITOOLS' fits_pixsize reads them in mas.

Axes 3 and 4 get a linear WCS (WAVE in metres, TIME as MJD) when the channels or epochs are evenly spaced to 1 %; otherwise WAVEIRR/TIMEIRR are set and the CHANNELS/EPOCHS tables give the values.

ROTIR.check_sky_cube — Function
check_sky_cube(cube, meta, xmap, tess, data) -> NamedTuple
check_sky_cube(cube, meta, components, data) -> NamedTuple

Compare the visibilities OITOOLS computes from the cube with ROTIR's own, on the uv coverage of data and in units of its error bars.

data is one OIdata per epoch (a vector, matched to the cube's epochs in order) or a (nλ, nt) matrix as readoifits_multiepochs(...; polychromatic = true) returns. For each plane, OITOOLS's setup_nfft/image_to_vis and ROTIR's exact model are both evaluated at the same uv with the same intensity at the plane's λ. For several components the exact model is ROTIR's binary one, (Σ F_k · binary_phase_shift(uv, offset_k)) / Σ flux_k. With a vector of single-band epochs the plane whose λ is closest to the data's mean wavelength is used.

Returns chi2dist, Σ(Δ/σ)²/n over V², T3amp and T3φ (the χ² the image adds), and rel_dV, max_dV2 and rms_dT3phi_deg, per plane and the worst over all planes.
