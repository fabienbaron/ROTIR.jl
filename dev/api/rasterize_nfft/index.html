Rasterization & NFFT

Two alternative forward-model implementations that avoid building the dense polyft matrix. Both produce real-space images from polygon vertex coordinates and intensity weights.

See Direct imaging methods for a guide with usage examples and guidance on when to use each approach.

Rasterization

Exact polygon-to-pixel rendering via Sutherland-Hodgman clipping. Works entirely in image space — no Fourier transforms involved.

rasterize_adjoint! details

The adjoint operation is the exact transpose of the forward rasterization: the forward spreads polygon intensities into pixels weighted by overlap area; the adjoint gathers pixel values back to polygons weighted by the same overlap area.

grad[p] = pixel_weight[p] * pixsize^2 * sum_{iy,ix} res_img[iy,ix] * Area(tile_p ∩ pixel)

Both forward and adjoint are threaded over polygons using per-thread local buffers, reduced at the end.

NFFT

Fast polygon Fourier transform via Gauss-Legendre quadrature and the Non-uniform Fast Fourier Transform. Approximates the continuous polygon FT integral by placing quadrature points inside each quadrilateral and evaluating the resulting non-uniform exponential sum with a single adjoint NFFT.

Return value layout

polyft_nfft_forward returns a Complex{T} array of shape (nx÷2+1, nx) in the standard rfft layout:

  • Rows correspond to rfftfreq(nx, 1/pixsize) — non-negative spatial frequencies from 0 to the Nyquist frequency 1/(2*pixsize) cycles/mas.
  • Columns correspond to fftfreq(nx, 1/pixsize) — the full frequency axis in standard FFT order (zero-frequency at index 1).

This layout is compatible with Julia's irfft(F, nx) to recover the real-space image. Apply fftshift to center the image:

img = fftshift(irfft(F, nx))

Convention notes

The NFFT.jl adjoint computes sum_j f_j exp(+2*pi*i * k . x_j). By negating the sample positions (pos = -r/L where L = nx*pixsize), the adjoint directly produces the standard DFT convention F[k] = sum f_j exp(-2*pi*i * k . r_j). The ifftshift then converts from NFFT natural order (k = -N/2, ..., N/2-1) to FFT order (k = 0, 1, ..., N/2-1, -N/2, ..., -1), and extracting the first nx÷2+1 rows gives the rfft layout.

build_gauss_samples details

For each visible polygon, build_gauss_samples parameterizes the quadrilateral using bilinear shape functions on [-1,1]^2, optionally subdivides into nsub x nsub sub-squares, and places ngauss x ngauss tensor-product Gauss-Legendre nodes in each sub-square.

Returns (xs, ys, fs) where:

  • xs, ys: spatial positions (mas) of the quadrature points
  • fs: complex weights including the intensity, Jacobian, and Gauss weight

Total samples: (ngauss * nsub)^2 * Npix.

Sky images for OITOOLS

FITS cubes OITOOLS can compute visibilities from; see the Exporting sky images for OITOOLS guide.

ROTIR.sky_layout — Function
sky_layout(img_north_west) -> Matrix

The (north, west) image polyft_nfft_image returns, as OITOOLS's (east, north) array with the centre at nx÷2+1. A transpose, a reflection of the first axis, and a one-pixel shift: the reflection of an even-length axis by reverse moves the centre pixel by one, and putting it back is what turns closure-phase agreement into complex-visibility agreement.

ROTIR.sky_grid — Function
sky_grid(params, tess, tepochs; data, oversample = 4, fov_factor = 6.0, min_nx = 256, pixsize, nx)
sky_grid(components, tepochs; ...)
    -> (; pixsize, nx, diameter, extent, mb_per_plane, reason)

A pixel size and image size for a sky cube, with the reason for each.

Pixel size: 1/(2ρmax)/oversample, ρmax the longest baseline in the data (cycles per radian) — Nyquist with room to spare. Without data, 1/64 of the largest stellar diameter.

Image size: the whole system plus a margin of (fov_factor − 1) diameters of the largest star — for one star, fov_factor diameters — rounded up to an even 2·3·5-smooth size. Six diameters, not two, MEASURED: a band-limited image rings beyond the limb and a tight field folds that back in, so OITOOLS's agreement with ROTIR on the ζ And coverage goes 1.3e-4 → 3e-5 (closure phases 0.28° → 0.05° rms) from 2× to 4× the diameter, and on to ~5e-6 at ~12×.

min_nx = 256 FLOORS the size: images that size are routine in interferometry, cost a fraction of a second per plane, and a bigger field only helps — at the ζ And pixel, 256 px is ~11 diameters and brings OITOOLS within ~5e-6 of ROTIR. The fov_factor margin is what governs once the system itself is large.

A BINARY'S FIELD GROWS WITH ITS SEPARATION while the pixel stays fixed by the baselines, so a wide pair costs nx² per plane: mb_per_plane says how much (Float32), and the caller decides.

ROTIR.render_sky_cube — Function
render_sky_cube(params, xmap, tess; tepochs, wavelengths, pixsize, nx,
                rendering = :bandlimited, intensity_model = :linear,
                normalize = :plane, secondary = nothing, mjd = nothing,
                T = Float32) -> (cube, meta)
render_sky_cube(components; tepochs, wavelengths, ...) -> (cube, meta)

The surface xmap (on tess, with geometry params) — or several components, see above — as sky images: an (nx, nx, nλ, nt) array in OITOOLS's layout (see sky_layout), one plane per wavelength and epoch.

  • tepochs are ROTIR epoch times (the same numbers create_star_multiepochs takes); mjd, when given, is recorded alongside them.
  • wavelengths in metres. With intensity_model = :linear (Rayleigh–Jeans) every channel has the same SHAPE; with :planck the contrast — and a binary's flux ratio — change with λ.
  • rendering: :bandlimited (default; reproduces ROTIR's visibilities in OITOOLS to ~1e-5) or :area (positive, flux-conserving, for display). See the file header.
  • normalize: :plane — every plane sums to 1, what OITOOLS imaging expects; or :relative — physical relative flux across channels and epochs (the λ⁻⁵ or λ⁻⁴ the dimensionless conversions drop is put back), scaled so the brightest plane sums to 1. Keeps the SED and the light curve.
  • bandwidths (m), optional: recorded as EFF_BAND in the CHANNELS table, like OI_WAVELENGTH. The planes themselves are monochromatic at wavelengths.

meta carries everything write_sky_cube records and check_sky_cube needs: pixel size, wavelengths, epochs, per-plane flux before normalisation, rendering, intensity model, the components and their parameters (meta.params is the first component's).

ROTIR.write_sky_cube — Function
write_sky_cube(path, cube, meta; comment = "") -> String

Write a cube from render_sky_cube as FITS: the (nx, nx, nλ, nt) primary array with a celestial WCS, plus CHANNELS and EPOCHS tables and the model's parameters (PARAMS).

THE HEADER DESCRIBES THE ARRAY OITOOLS ACTUALLY USES, which is not quite what OITOOLS's own writefits says about it: the first axis increases EAST, so CDELT1 > 0 (RA increasing with index), and the reference pixel is nx÷2+1, the NFFT phase centre (writefits writes a negative CDELT1 and CRPIX = nx/2). Degrees, per the FITS standard, with CUNIT stated; OITOOLS's fits_pixsize reads it back in mas.

Axes 3 and 4 get a linear WCS (WAVE in metres, TIME as MJD) only when the channels or epochs are evenly spaced to 1 %; otherwise the header says so and the tables are the authority, because FITS cannot express an irregular axis without the -TAB convention.

ROTIR.check_sky_cube — Function
check_sky_cube(cube, meta, xmap, tess, data) -> NamedTuple
check_sky_cube(cube, meta, components, data) -> NamedTuple

How faithfully OITOOLS, given this cube, reproduces ROTIR's own visibilities — measured on the data's uv coverage, in units of the data's error bars.

data is one OIdata per epoch (a vector, matched to the cube's epochs in order) or a (nλ, nt) matrix as readoifits_multiepochs(...; polychromatic = true) returns. For each plane, OITOOLS's setup_nfft/image_to_vis and ROTIR's exact model are both evaluated at the same uv with the same intensity at the plane's λ, so the comparison isolates the IMAGE, not the physics. For several components the exact model is ROTIR's binary one, (Σ F_k · binary_phase_shift(uv, offset_k)) / Σ flux_k. With a vector of single-band epochs the plane whose λ is closest to the data's mean wavelength is used.

Returns chi2dist — Σ(Δ/σ)²/n over V², T3amp and T3φ, the χ² the image itself would add — and rel_dV, max_dV2, rms_dT3phi_deg, per plane and worst over all planes.
